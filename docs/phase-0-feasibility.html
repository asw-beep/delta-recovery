Phase 0 · Razorpay Buildathon 2026 · Track 03

Recovery Rails Audit

What an AI revenue-recovery agent can actually execute against Razorpay Test Mode — and the four things it categorically cannot, which the product design has to route around.

Date 22 Aug 2026 Status Pre-implementation Sources 31 official doc pages Code written None

Bottom line

The concept is buildable, but not as written. Razorpay has no API that retries a failed payment — and Razorpay already ships a competing product. Both facts reshape the build.

Detection, diagnosis, decisioning, execution, verification and measurement can all run on real Test Mode infrastructure. The execution verbs available to us are narrower than Section 8 of the master context assumes: we can create and re-notify payment links and invoices, cancel them, pause/resume subscriptions, and escalate. We cannot re-charge a failed payment, we cannot detect checkout abandonment from an event, and we can only create 30 payment links in test mode.

The strategic consequence is the useful one. Because the retry mechanic is unavailable and Razorpay's own Agent Studio already automates the obvious version of this, the differentiator cannot be the action. It has to be the decision: an uplift-optimising policy kernel that predicts incremental recovery, prices every intervention against contact fatigue and cost, refuses actions it cannot justify, and proves the whole thing on a held-out set against an oracle ceiling. That is the section of the problem Razorpay's shipped products do not expose, and it is where the prize is.

AProduct feasibility

Can the DETECT → DIAGNOSE → DECIDE → ACT → VERIFY → MEASURE loop close on real Razorpay Test Mode infrastructure?

Yes, with three amputations. Taking the loop stage by stage:

StageFeasible on Test Mode?Mechanism
DetectYespayment.failed webhook, plus a reconciliation poll over GET /v1/payments and GET /v1/orders?expand[]=payments to catch what webhooks miss.
DiagnoseYesReal, documented error taxonomy on the failure payload: error_source, error_step, error_reason, error_code. Plus the Downtime API for infrastructure-level root cause.
DecideYesEntirely ours. Nothing to integrate.
ActPartlyPayment link creation, link/invoice re-notification, cancellation, subscription pause/resume all work. Re-charging a failed payment does not exist as an API. See §C.
VerifyYespayment_link.paid, invoice.paid, order.paid webhooks, with attribution carried in notes and reference_id.
MeasureYesOur ledger. The honest number requires a counterfactual, which is why §G and §I matter more than the integration.
LearnOffline onlyTest Mode cannot generate enough real volume to train on. Model trains on the synthetic generator; the live path only executes the learned policy.

The three amputations

  1. No payment retry. The action set collapses from "retry, then nudge" to "nudge with a fresh payment instrument". The agent's job shifts from scheduling retries to choosing whether, when, how and whom to contact — which is, fortunately, the harder and more interesting problem.
  2. No abandonment event. Checkout drop-off must be inferred from order state ageing. Defensible, but it is inference and the report/UI must say so.
  3. No live learning loop. Test Mode volume is too thin. The learning claim must be made on the synthetic experiment, not on the demo account.
Framing risk

The master context's Section 17 demo script ("214 → payment retry") is not executable. Rewriting that beat is not cosmetic — it is the difference between a demo that survives a judge's question and one that doesn't. §J proposes the replacement.

Webhook mechanics

  • Signature: HMAC-SHA256 over the raw, unparsed body, keyed with the webhook secret, delivered in X-Razorpay-Signature. SDK helpers exist for Node and Python.
  • Must return 2xx within 5 seconds, or Razorpay retries with exponential backoff for 24 hours and then deactivates the webhook. This mandates persist-first, process-async.
  • Up to 30 webhook URLs per mode.
  • Test Mode webhooks are fully supported; setup requires the default OTP 754081.
  • No documented ordering or exactly-once guarantee. Design for both duplicates and reordering.

SDK and MCP

  • Official server SDKs: razorpay on npm (Node) and PyPI (Python). Both ship webhook signature validation. Basic Auth, base https://api.razorpay.com/v1.
  • MCP server is real and official — remote at https://mcp.razorpay.com/mcp over HTTP transport with base64 Basic credentials, or run locally with RAZORPAY_KEY_ID / RAZORPAY_KEY_SECRET and an optional --read-only flag. Roughly 50 tools including create_payment_link, send_payment_link, create_order, fetch_all_payments, fetch_order_payments. Notably create_refund is not supported on the remote server.
Position MCP correctly

MCP is a development-time and copilot surface. It is not the production integration path — a webhook-driven backend cannot depend on an interactive MCP session, and routing money actions through an LLM's tool call would violate the safety model in §H. We use MCP for exploration and for a merchant-facing read-only copilot; the pipeline uses the SDK. Say this explicitly in the README, because a judge who sees MCP presented as the backend will read it as a misunderstanding.

CGaps and hard limits

The things we cannot do. Each one is a design constraint, and several are demo-breaking if discovered late.

Gap 1 — blocking

There is no API to retry a failed payment. The Payments API surface is capture, fetch, update — nothing else. A payment in failed is terminal; the merchant cannot re-present it. The only genuine server-side re-charge is POST /v1/payments/create/recurring, which requires a saved mandate token and the Recurring Payments feature activated on the account by Razorpay Support. We should assume a fresh hackathon account will not have it.

Consequence: drop "retry payment" from the action vocabulary entirely. Never render the word "retry" next to a Razorpay action in the UI. What we actually do is issue a new payment instrument (a link) and manage the contact sequence around it.

Gap 2 — demo-breaking

Test Mode caps Payment Links at 30 per business. This directly kills any demo that claims to have executed hundreds of live recovery actions. Confirmed from Razorpay docs via search snippet — verify in dashboard on day 1, because the whole demo architecture depends on the number.

Consequence: the batch runs in a declared hybrid execution mode. A sampled subset (10–20 items) executes against the real Razorpay API and produces real plink_ IDs, real SMS/email dispatch, real payment_link.paid webhooks. The remainder runs through a deterministic simulator built from the same generator as §G. Every row in the UI carries a LIVE or SIM badge, and the headline metric shows both. Presenting simulated actions as real Razorpay transactions is the single fastest way to lose this competition.

Gap 3

There is no checkout-abandonment webhook. No checkout.abandoned event exists. Abandonment must be inferred: an order in created (never attempted) or attempted (attempted, all payments failed) that has aged past a threshold and has amount_due > 0. Since GET /v1/orders has no status filter, we sweep by time window with expand[]=payments and classify locally.

Consequence: abandonment detection is a heuristic with a tunable threshold, and the UI must label it as inferred. It also means the risk item can be wrong — the customer may still be mid-checkout — which is exactly why the policy engine needs a minimum dwell time before any contact.

Gap 4

payment.failed does not fire for every failure. Razorpay's own docs state it "is not triggered if the payment fails during authorisation (while making the first payment)." Webhook-only detection therefore systematically undercounts.

Consequence: we need a reconciliation sweep alongside the webhook listener, and the two must converge on the same risk item without duplicating it. Building this deliberately — and showing the reconciliation catching what the webhook missed — is a genuine production-engineering signal that most submissions will not have.

Further limits, in descending severity

Gap 5 — competitive, not technical

Razorpay already ships this product. Failed Payment Recovery (automatic personalised links to customers whose payment failed), Intelligent Payment Retry (next-best-action at checkout), subscription Smart Retries, and Agent Studio — currently early access — whose advertised agents include Subscription Recovery ("analyses failed subscription payments, applies retry logic, triggers customer nudges") and Abandoned Cart Conversion.

We will be judged by people who built those. A submission that presents "an AI agent that detects failed payments and sends recovery links" as novel will read as not having done the homework. This is the most important finding in this report and it is addressed in §D and §H.

DRecommended MVP

The smallest build that clears Track 03's stated bar — measured money recovered across a batch, compliant escalation, stopping rules, audit trail — while being defensibly different from what Razorpay already sells.

The one-sentence product

A recovery agent that optimises incremental recovered rupees per unit of customer patience — and can prove, on a held-out set, that it beats both doing nothing and chasing everything.

The pivot from the master context is one word: incremental. Every naive recovery system optimises P(customer pays). That over-counts badly, because a large share of failed payments and abandoned carts recover on their own — the customer just tries again. Contacting those people generates zero incremental revenue, real cost, and real annoyance. The right objective is uplift:

uplift(a | x)  =  P(pay | x, action a)  −  P(pay | x, do nothing)

EV(a | x)      =  uplift(a | x) · amount  −  cost(a)  −  λ · fatigue(x, a)

policy(x)      =  argmax EV over actions the policy engine permits;
                  do-nothing is always in the set, with EV = 0.

This single choice cascades into the whole design: it dictates the synthetic generator (must produce potential outcomes for every arm), the model (two-arm uplift, not a single classifier), the evaluation (oracle ceiling and a do-nothing floor, not just a retry-everything baseline), and the demo's most surprising moment (the agent declining to contact a customer who was going to pay anyway, and being right).

The policy engine, concretely

Deterministic, pure, unit-tested, evaluated after the model proposes and before anything executes. Emits ALLOW / DELAY / ESCALATE / STOP plus an ordered reason list.

Quiet hours and the fatigue cap are what the track means by "compliant escalation". They are also the rules most likely to make a judge nod, because they are the ones a real payments team would insist on and a hackathon team would forget.

Explicitly out of scope for MVP

Voice, Hinglish, WhatsApp, multi-channel orchestration, A/B or bandit optimisation, revenue forecasting, refunds, disputes. Each is a Section 28 extension. Depth over breadth — and several are unbuildable anyway given the notify_by template constraint in §C.

EArchitecture

Two runtimes, one database, and a hard boundary between what reasons and what decides.

Degradation

Master context §24 demands graceful failure. The boundary makes it easy to honour: if the LLM is down, diagnosis falls back to the deterministic taxonomy string and the loop runs unchanged. If the scoring service is down, the policy engine forces ESCALATE rather than guessing. If Razorpay is down, actions queue and the idempotency ledger prevents double-execution on recovery. If the database is down, the webhook receiver returns non-2xx and relies on Razorpay's 24-hour retry — which is the correct behaviour, not a bug.

Three constraints that carry the safety argument

  • webhook_events.razorpay_event_id UNIQUE — duplicate delivery becomes a no-op at the database level, not a code path that might have a bug.
  • action_attempts.idempotency_key UNIQUE, written before the outbound call — a crash mid-flight cannot produce a second link.
  • Partial unique index on risk_items where state = 'open' — the webhook path and the reconciliation path cannot open two risk items for the same payment.

Being able to point at these three in a demo is worth more than another dashboard panel. They are the difference between claiming idempotency and having it.

Generating process

Documented as an explicit causal chain, committed alongside the code so the data-generating process is auditable:

Customer   latent_reliability ~ Beta(a,b) · payday_day ~ {1,7,25}
            tenure · past_success_count · past_failure_count · ltv_band

Order      amount ~ LogNormal(μ_vertical, σ) · method ~ Categorical(vertical)
            bank ~ Categorical(method) · timestamp → hour, weekday

Failure    P(fail) = f(method, bank, amount, hour, downtime_active,
                          customer.latent_reliability)
            error_reason ~ Categorical conditioned on the failure cause
            → transient causes ⇒ transient reasons; dead instruments ⇒ instrument reasons

Downtime   Poisson-arrival windows per (method, bank), 20–180 min,
            inflating P(fail) inside the window

Outcomes   For EVERY risk item, draw the FULL potential-outcome vector:
            Y(do_nothing), Y(link), Y(link+sms), Y(link+email), Y(escalate)
            Y(a) = Bernoulli( p_base(x) + uplift(x, a) ), correlated across arms

Controlled relationships

These are the structure the model has to learn, and each one is a defensible claim about real payment behaviour:

  • Transient failures have high self-recovery — which is precisely why uplift from contacting them is lower than raw probability suggests. This is the trap that catches naive systems, and it is deliberately built in.
  • Instrument-dead failures have near-zero self-recovery and near-zero uplift from a same-instrument nudge, but meaningful uplift from an alternative-method link.
  • insufficient_funds uplift is strongly time-dependent — near zero immediately, substantial near the customer's payday.
  • Uplift decays with contact count; the third contact in a week has negative net EV for most amounts.
  • Customers with long successful history self-recover more — again suppressing uplift.
  • Contacting during an open downtime window has depressed uplift, because the customer's second attempt fails too.
  • Amount correlates with self-recovery (people chase their own large purchases) but also raises EV per point of uplift. The tension is real and the policy has to resolve it.

Logging policy

Why this matters

The historical action in the training log is assigned by a randomised ε-greedy policy, not by a rule. This makes the training data unconfounded, so the per-arm outcome models are unbiased and off-policy evaluation is valid. If the log were generated by a sensible rule, every model trained on it would inherit that rule's blind spots — and the evaluation would be circular. Explaining this in the README is a strong ML-maturity signal.

Splits

Grouped by customer and by time simultaneously: train on days 1–60, validate on 61–75, test on 76–90, with no customer appearing across the train/test boundary. This prevents both leakage of customer traits and leakage of temporal structure. The test set is generated once, hashed, and not touched until the final evaluation run.

Where the LLM does propose an action, the path is: schema-validated structured output → typed proposal → policy engine → executor. The LLM cannot name an endpoint, cannot set an amount, and cannot bypass a rule. It selects from an enum of actions the policy engine will independently re-validate. If its proposal disagrees with the EV ranking, that disagreement is recorded — and a panel showing where the model and the LLM disagreed is a genuinely interesting artifact for the demo.

The uplift model

A T-learner: one calibrated model per action arm plus a control arm, each predicting P(pay within the window). Uplift is the difference. Rationale over a single classifier: we need incremental effect, and a single P(recover) model systematically over-recommends contact on exactly the items that self-recover.

ChoiceDecision
EstimatorStart with regularised logistic regression. Move to LightGBM only if held-out AUC-PR improves materially. Interpretability is worth more here than a small lift — per master context §13.
CalibrationIsotonic on the validation split. Mandatory — the EV formula multiplies probability by rupees, so a miscalibrated model produces confidently wrong money decisions.
Featuresamount, method, bank, error_source/step/reason, hours since failure, hour-of-day, weekday, days to payday, customer success/failure counts, tenure, LTV band, prior contacts in window, downtime-active flag, risk class.
ExplainabilityPer-decision coefficient contributions surfaced in the audit view. "Recovery probability 0.81" is unfalsifiable; "0.81, driven by transient bank error (+0.22) and four prior successes (+0.14)" is a product.
Failure modeIf the scoring service is unreachable or the item falls outside the training distribution, the policy engine returns ESCALATE, never a default probability.

IEvaluation design

Four comparators, not one. The oracle ceiling is what turns "we beat retry-everything" into "we captured 78% of the achievable recovery" — a far harder claim to dismiss.

Comparators

IDPolicyWhat it establishes
B0Do nothingThe floor. Whatever recovers here recovers on its own — and every rupee below this line is not ours to claim. Most submissions will not have this baseline, and its absence is what makes their numbers inflated.
B1Contact everything onceThe naive agent. The master context's proposed baseline.
B2Industry dunning ladderFixed nudges at day 0 / 3 / 7. What a competent team ships without ML.
AOur agentUplift-EV + policy engine.
ORACLEPerfect foresightChooses the best arm using the true potential outcomes. Unachievable by construction — it defines the ceiling and converts our result into "% of achievable captured".

Protocol

  1. Generate the dataset with a fixed seed. Hash and commit the test split. Do not open it.
  2. Develop and tune on train + validation only.
  3. Freeze the model, the policy config and the cost table. Record versions.
  4. Run all five policies over the identical held-out risk items, reading each policy's chosen arm from the potential-outcome table.
  5. Bootstrap 1,000 resamples for 95% confidence intervals on every headline number. A point estimate without an interval is not evidence.
  6. Cross-check with inverse-propensity and doubly-robust off-policy estimates on the logged data — if these disagree materially with the potential-outcome result, something is wrong and we say so.
  7. Commit results as JSON. Every figure in the README and the demo reads from that file. Nothing is typed by hand.
Non-negotiable

No number appears anywhere — slide, README, dashboard — that is not produced by a committed run over the held-out set. If the improvement turns out to be 9% rather than 60%, we report 9% and explain the ceiling. A modest honest result with an oracle bound and confidence intervals will outscore a spectacular unverifiable one in front of this particular set of judges.

JDemo

Four and a half minutes. Two live Razorpay round-trips, one deliberate refusal, and one moment that reframes the problem.

  • 0:00Cold open — the reframe. Dashboard shows ₹18.4L at risk. Then the second number: "Of that, ₹6.1L will recover on its own. We only get paid for the difference." This is the thesis, and it lands in fifteen seconds. It also immediately separates us from every other Track 03 submission.
  • 0:30Diagnosis. Open one failed payment.   • 1:00The recovery plan. The batch, grouped by chosen action, each row showing uplift, EV and policy verdict. Point at the STOP rows: "142 items we're deliberately not touching."
  • 1:30Execute — live. Run the batch. A sampled subset hits the real Razorpay API. Show a real plink_ ID appearing, and open it in the Razorpay test dashboard in a second tab. Every row badged LIVE or SIM, and say out loud why: "Test mode caps us at 30 links, so twelve of these are real and the rest replay the simulator. Here are the twelve." Volunteering the constraint converts a weakness into a credibility signal.
  • 2:15Verification. Pay one live link on a phone. The payment_link.paid webhook lands, the outcome row writes, the recovered figure ticks up on screen. This is the moment the loop visibly closes — end to end, on real infrastructure.
  • 2:45The refusal. Force an action on an item already contacted three times this week. Policy engine returns STOP with the reason chain rendered: contact fatigue cap → 3/3 in trailing 7 days → routed to human queue.   • 3:15The distinctive one. A downtime window opens. Six pending actions flip to DELAY automatically. "HDFC netbanking is down right now.   • 4:15Audit trail. One decision, top to bottom: raw webhook → diagnosis → per-arm scores → EV → policy verdict with reasons → idempotency key → API request and response → verifying event → recovered amount. Close on it. "Every rupee on that dashboard traces to a row like this one."

Sequencing note

M4 before M5–M7 is the deliberate inversion of the obvious order, and it is the most important scheduling decision here. Building the evaluation harness and all three non-ML baselines before the agent exists means we discover early whether the problem is even hard — if B2 already captures 95% of the oracle, the agent has almost no room and we should change the problem framing while there is still time. Discovering that in the last two days would be fatal.
