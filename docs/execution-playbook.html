Recovery Rails Playbook

Everything decided in advance so no build hour is spent deciding: the stack, the seven days, what to assemble rather than author, and the tactics that win rooms.

Budget ~56 h Runtime One — TypeScript Risk classes 1 (+1 stretch) Companion Recovery Rails Audit

How this week is won

Assemble aggressively, author only the three things that are actually the submission: the uplift model, the policy engine, and the evaluation harness.

Every other component is a solved problem with a library or a copy-paste source, and treating it as one is not cutting corners — it is the correct allocation. A judge will never award a point for a hand-rolled HMAC check or a bespoke data table. They will award points for a system that decides well, refuses correctly, and can prove its number.

The three rules that govern every decision below: one runtime (TypeScript everywhere except an offline training script), deploy on day one (never leave deployment to the end), and the evaluation harness ships before the agent does (so you cannot accidentally tune against your own test set, and so you discover on Day 3 rather than Day 7 whether the problem is hard enough to be worth solving).

01Operating principles

Five rules. When a decision comes up mid-build and you are tired, resolve it with these instead of thinking.

1 — Author only the differentiator

Three files are the submission: the uplift scorer, the policy engine, and the evaluation harness. They get your best hours and full test coverage. Everything else is plumbing, and plumbing gets libraries, generators, and copy-paste.

2 — Deterministic core, LLM at the edges

Money arithmetic, probabilities, expected value, policy verdicts, idempotency, execution — all pure TypeScript, unit-tested, no model in the path. The LLM does diagnosis narrative, action proposal (schema-validated, then re-validated by the policy engine anyway), recovery message copy, and the merchant copilot. When a judge asks "what if the LLM hallucinates?", the answer is a code path you can point at, not a reassurance.

3 — One runtime

TypeScript for everything that runs in production. Python exists only as an offline training script that emits a JSON file. No second service, no second deploy target, no cross-language debugging at 2am.

4 — Ship the skeleton on Day 1

Deployed, public, receiving real Razorpay webhooks before you write a line of business logic. Teams that leave deployment to the end lose the last day to it, every time.

5 — Never fake, always label

Test Mode caps payment links at 30. Some of the batch will be simulated. Every simulated row carries a SIM badge, and you say it out loud in the demo before anyone asks. Volunteering a constraint reads as rigour; being caught by it reads as deception, and it is the one mistake there is no recovering from in a judged room.

The stack decision that saves the most time

Exporting the trained model as JSON and scoring in TypeScript eliminates an entire service. Logistic regression scoring is a dot product and a sigmoid; isotonic calibration is a sorted lookup with linear interpolation. Forty lines. You lose nothing — the model is trained by scikit-learn with proper calibration either way — and you delete a deployment, a cold-start problem, a network failure mode, and a whole language from the production path.

04LLM architecture

Gemini primary, Groq fallback, OpenRouter optional. One adapter, one Zod schema per task, hard boundary at the policy engine.

Provider chain

RankProviderRoleNotes
PrimaryGemini — current free-tier flash model via AI StudioAll reasoning tasksBest intelligence-per-rupee at free tier. Native JSON mode. Confirm the exact model id and daily quota in AI Studio on Day 1 — they move.
FallbackGroq — llama-3.3-70b-versatile or current catalogue equivalentAutomatic failover, and the demo-day safety netVery fast, which matters if a batch makes sequential calls. Verify the model id is still listed before demo day.
OptionalOpenRouterModel switching without code changesAdd only if you actually want to swap models. One env var, no new code path.

The adapter

// lib/llm.ts — one file, provider-agnostic, schema-enforced
import { generateObject } from 'ai';
import { google } from '@ai-sdk/google';
import { groq }   from '@ai-sdk/groq';

const CHAIN = [
  google('gemini-2.5-flash'),          // primary
  groq('llama-3.3-70b-versatile'),     // fallback
];

export async function propose<T>(schema: ZodSchema<T>, prompt: string): Promise<T | null> {
  for (const model of CHAIN) {
    try {
      const { object } = await generateObject({ model, schema, prompt, maxRetries: 1 });
      return object;                    // already Zod-validated by the SDK
    } catch { /* try next provider */ }
  }
  return null;                          // ← every caller MUST handle null
}

Returning null rather than throwing is deliberate. It forces every call site to have a non-LLM path, which is how the system stays working when both providers are down — the state in master context §24 that most submissions handle by crashing.

The split, concretely

TaskOwnerFallback if LLM unavailable

The trick that makes batch LLM use viable

Cache LLM output by (taxonomy_class, amount_band, risk_class), not by item. A 200-item batch then makes roughly 8 calls instead of 200. Free tiers survive it, the batch finishes in seconds on stage instead of minutes, and the diagnosis is arguably better — items in the same class genuinely share a diagnosis, and identical explanations for identical situations reads as consistency rather than repetition. Build this on Day 4, not as an optimisation later.

Hard boundary

The LLM selects from an enum. It cannot name an endpoint, set an amount, choose a recipient, or bypass a rule. Its proposal is re-validated by the policy engine, which would have reached its own verdict regardless. Record every disagreement between the LLM's proposal and the EV ranking in the decisions table — a panel showing where they diverged is a genuinely interesting demo artifact and costs one column.

06The seven days

Eight hours a day. Each day ends on a gate that must pass before the next begins. If a gate fails, cut scope from the cut ladder — never slip the day.

Day 1Verify reality, then deploy an empty shell8 h
  • 0–1Razorpay test account. Generate test keys. Empirically confirm the payment-link cap by creating links until it refuses. Check whether Invoices and Subscriptions are enabled. Write findings into DECISIONS.md.
  • 1–2create-next-app, shadcn init, add the eight components you will need, GitHub repo, .env.example committed and .env ignored in the first commit.
  • 2–4Supabase project, Drizzle setup, full schema from audit §F, first migration applied.
  • 4–6Webhook route: SDK signature verification on the raw body, persist to webhook_events with the unique event-id constraint, return 200 immediately. Zero business logic.
  • 6–7Deploy to Vercel. Register the webhook in the Razorpay dashboard — OTP 754081.
  • 7–8Fire a real test payment. Watch the row land in production.

Gate A real Razorpay test event is stored in production Postgres, and the link cap is a number you have measured rather than read.

Day 2Ingestion and detection8 h
  • 0–3Async processor: raw event → normalised payments / orders. Order-independent — state derives from entity status, never arrival sequence.
  • 3–5Failed-payment detection → risk_items, with the partial unique index on open items doing the deduplication.
  • 5–7Reconciliation sweep over GET /v1/payments, wired to Vercel Cron. Must converge with the webhook path without opening a second risk item.
  • 7–8Tests: duplicate event, out-of-order arrival, bad signature, malformed body, unknown event type.

Gate Suppress a payment.failed webhook deliberately; reconciliation still detects it, exactly once.

Day 3The generator and the harness — the day that decides the project8 h
  • 0–4generate.py: 2,000 customers, 14,000 orders, 90 days, with the full potential-outcome vector per risk item and a randomised ε-greedy logging policy. Build in high self-recovery on transient failures — that is the trap the agent must learn to avoid.
  • 4–5Grouped splits: customer and time. Hash the test split. Seal it.
  • 5–8harness.py: run B0 do-nothing, B1 contact-everything, B2 day-0/3/7 ladder, ORACLE. Bootstrap intervals. Write results.json.

Gate Four baselines with confidence intervals exist before any model does — and the gap between B2 and ORACLE is wide enough that an agent has room to win. If it is not, the data is too easy; fix it today.

Day 4Diagnosis and the model8 h
  • 0–2taxonomy.ts: the five classes from audit §B. Unmapped error_reason values raise rather than defaulting to a bucket.
  • 2–5train.py: two-arm logistic regression, isotonic calibration on validation, export coefficients and the calibration table to model.json. Commit the reliability curve as a PNG — it is a strong README artifact.
  • 5–7uplift.ts: read model.json, score both arms, return uplift plus per-feature contributions. Unit-tested against fixtures from the Python side so both implementations provably agree.
  • 7–8llm.ts with the provider chain, and the class-level diagnosis cache.

Gate TypeScript scoring matches Python scoring to six decimal places on a fixture set. If they diverge, everything downstream is unfalsifiable.

Day 5Decide, execute, verify8 h
  • 0–2ev.ts and policy.ts: every rule from audit §D, each emitting an attributed reason. One test per rule proving it blocks.
  • 2–5executor.ts: idempotency row written before the call, state re-read from Razorpay immediately before acting, p-limit concurrency, p-retry on 429, LIVE/SIM modes.
  • 5–6Attribution: payment_link.paid → match on notes.decision_id → write the outcome row with the recovered amount.
  • 6–8Resend + LLM-written recovery email carrying the Razorpay short_url. This is the demo's warmest beat — the message lands on your phone on stage.

Gate Kill the process mid-batch, restart, and produce zero duplicate payment links. Verified by running it, not by reading the code.

Day 6Dashboard — one full day, no more8 h
  • 0–2Overview: revenue at risk, the self-recovery split, incremental opportunity, recovered, action count, escalations. The split is the thesis — give it the most visual weight on the page.
  • 2–5Recovery queue: TanStack Table, one row per risk item showing diagnosis, uplift, EV, policy verdict, LIVE/SIM badge. Plus the Execute Batch button.
  • 5–7Decision drilldown: raw event → diagnosis → scores → EV → policy verdict with reasons → idempotency key → request/response → verifying event → recovered amount. Top to bottom on one page.
  • 7–8Evaluation page rendering results.json. Two charts maximum.

Gate Every number on screen traces to a row you can open in front of someone. Shadcn defaults throughout — design nothing custom.

Day 7Freeze, prove, rehearse8 h
  • 0–2Five failure drills: duplicate webhook, out-of-order, already-paid guard, idempotency crash, LLM unavailable. Each one demonstrable in the UI.
  • 2–3Freeze. Open the test set once. Run all five policies. Commit results.json. Whatever it says is what you claim.
  • 3–5README: 60-second explainer, screenshots, Mermaid architecture diagram, honest limitations section, results table read from the JSON.
  • 5–6Demo reset button, seed script, keyboard-driven run-through.
  • 6–7Record the backup video. One clean take. This is insurance against a dead network on demo day.
  • 7–8Three timed rehearsals, one on a deliberately throttled connection.

Gate Three clean runs under 4:30, a recorded backup, and a README that would score well if nobody ever watched the demo.

07Token discipline

How to keep the build moving on the hard parts instead of on boilerplate and re-derivation.

Before you ask for code

  • Lock the decisions in DECISIONS.md. Stack, schema, action enum, policy rules, file layout. Every decision that lives in the file is one that never gets re-derived at the top of a session — and re-derivation is where most of the cost goes.
  • Scaffold with CLIs, not with me. create-next-app, shadcn add, drizzle-kit generate. Boilerplate written by a generator costs nothing.
  • Define types first, implement second. Ask for schema.ts and the shared types in one request. Everything after that is written against a fixed contract instead of inventing one each time.

While building

  • Batch related files into one request. "Write ev.ts, policy.ts and their tests" costs far less than three separate asks, because the context is loaded once.
  • Ask for whole files on first write. Incremental refinement of a file that does not exist yet is the most expensive way to get it.
  • Never ask for a read-back after an edit. If an edit succeeded, it succeeded.
  • Paste the error, not the log. Ten relevant lines beat a thousand-line stack trace.
  • Run the Python yourself. Iterate on generate.py and train.py in your own terminal; bring back only the exception you cannot resolve. Training loops are not worth agent turns.
  • Do not have the agent drive the dev server. Watching the browser repeatedly is expensive and you are faster at it.
  • /compact at day boundaries, never mid-task. Compacting between Day 4 and Day 5 costs nothing; compacting mid-debug loses the thread and you pay to rebuild it.

Spend freely on

uplift.ts, policy.ts, executor.ts, the eval harness, and the failure drills. These are where correctness is subtle, where bugs are invisible until a judge finds them, and where the submission actually lives. Everywhere else, the cheapest working thing wins.

08Champion tactics

The things that separate a good build from a winning submission, most of which have nothing to do with code.

The README is the second demo

Judges read repositories, often before or instead of watching a demo, and frequently while deciding between two similar submissions. Open with a screenshot and a sixty-second explainer — what it does, the one insight, the measured result. Then the Mermaid architecture diagram, then the results table, then an honest limitations section. That last one is counterintuitive and it works: a limitations section signals someone who understands their own system, and it pre-empts every question a judge was going to ask.

Commit like a team, not like a dump

Small, frequent, well-messaged commits across all seven days. A repository whose history is one 6,000-line commit at 3am reads as generated. One whose history shows schema, then ingestion, then policy, then tests, reads as engineered. This costs nothing and is checked more often than people expect.

Build the reset button

One endpoint that restores the demo to its starting state in two seconds. You will rehearse eight times. Without it you will spend forty minutes of Day 7 re-seeding by hand, and you will be unable to re-run cleanly if the first live attempt fails in front of judges.

Record the backup on Day 7, not demo day

A clean screen recording of the full run. If the network dies, you narrate over video and lose almost nothing. Teams that skip this and hit a dead connection lose everything.

Lead with the number, not the architecture

The first fifteen seconds decide whether anyone listens to the next four minutes. Open with "₹18.4L is at risk — but ₹6.1L of that recovers on its own, so we only get paid for the difference". Not with a stack diagram. The architecture earns its place in the README and in Q&A.

Rehearse the refusal beat hardest

Track 03 explicitly asks for stopping rules and compliant escalation. Most submissions will mention them; almost none will demonstrate one blocking a real action live, with the reason chain rendered on screen. That beat is where the track's stated bar is directly satisfied, so it deserves more rehearsal than anything else in the run.

Volunteer the constraints

Say "test mode caps us at 30 links, so twelve of these are real — here they are" before anyone asks. Say "this is inferred from order ageing, not an event, because Razorpay has no abandonment webhook." Every constraint you name yourself converts from a vulnerability into evidence that you read the documentation properly.

Two small things with outsized returns

  • Name the product. A named product with a wordmark in the header is remembered; "our submission" is not.
  • Freeze twelve hours before the deadline. Nothing merges after the freeze. Submission-day bugs come almost entirely from last-minute changes, and the marginal feature never outweighs the risk.

10Cut ladder

Falling behind is expected. Cut in this order, without deliberating — the order is already the deliberation.

#CutCost of cutting
1Merchant copilotNone. It is a nice-to-have that no judging criterion asks for.
2LLM narrative → template stringsSmall. The loop is unchanged; only the prose gets flatter.
3Abandoned-checkout classSmall. One risk class done rigorously beats two done shallowly, and the track does not require breadth.
4Live payment beat → pre-recordedModerate. Costs drama, not credibility, provided you say it is recorded.
5Hinglish email → Razorpay notify_by onlyModerate. Loses the warmest beat but keeps a real Razorpay action.
6Failure drills 5 → 3Moderate. Keep duplicate-webhook, already-paid, idempotency-crash.
7Evaluation page → a table in the READMEModerate. The evidence survives; only its presentation degrades.
Never cut

The uplift model, the policy engine, the B0 + oracle evaluation, and the audit trail. These four are the submission. Everything above them is presentation, and presentation can be thin if the substance is real. If you find yourself considering a cut from this list, cut a whole day of dashboard work instead.

11Submission checklist

Repository

  • README opens with a screenshot and a 60-second explainer
  • Mermaid architecture diagram renders on GitHub
  • Results table generated from eval/results.json, with confidence intervals
  • Honest limitations section naming the link cap, the SIM split, and the inference-based abandonment
  • DECISIONS.md explaining why uplift rather than raw probability
  • .env.example present, .env absent from history, no key in any commit or screenshot
  • Commit history spread across all seven days
  • Setup instructions that a judge could actually follow

Product

  • Deployed, public URL, loads cold in under three seconds
  • Every number traces to a database row
  • LIVE / SIM badges visible at row level plus a persistent banner
  • Policy blocks show the rule that fired, in plain language
  • Demo reset endpoint works
  • Works with the LLM disabled

Evidence

  • Test set opened exactly once, and you can say so honestly
  • Five policies compared, including the do-nothing floor and the oracle ceiling
  • Bootstrap intervals on every headline figure
  • Wasted-contact rate reported, not hidden
  • Calibration curve committed
  • No figure anywhere contradicts results.json

Demo

  • Three timed runs under 4:30
  • Backup video recorded
  • Refusal and downtime beats work fully offline
  • Answer prepared for "what if the LLM hallucinates?"
  • Answer prepared for "your synthetic data — did you build a world you could beat?"
  • Answer prepared for "Razorpay already ships Failed Payment Recovery and Agent Studio — what's different?"
The three answers, prepared

Hallucination: "It cannot. The LLM selects from an enum and writes prose. Every number is deterministic, and the policy engine re-validates the proposal independently — here is the code path."

Synthetic data: "The generating process is committed and documented. I deliberately built in high self-recovery on transient failures, which is the case that punishes my own approach hardest. And the oracle ceiling bounds the claim — I report the percentage of achievable recovery captured, not just a win over a weak baseline."

Razorpay already ships this: "They do, and I cite them in the README. Those products optimise the probability that a customer pays. This optimises the incremental rupee — it declines to contact customers who would have paid anyway, which is most of them. That is a different objective, and it is why the wasted-contact rate is on my dashboard and not on theirs."

Model identifiers and free-tier quotas move. Confirm the current Gemini flash model in AI Studio and the current Groq catalogue entry on Day 1, and again before demo day. The adapter in §04 is written so that changing either is a one-line edit.

Companion document. This playbook assumes the constraints established in the Recovery Rails Audit — no payment-retry API, a 30-link test-mode cap, no abandonment webhook, and Razorpay's own shipped recovery products. Re-read audit §C before Day 1; every scoping decision here follows from it.
